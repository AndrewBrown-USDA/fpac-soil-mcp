# 40.2.2 -- Custom route reachability evidence

## Result

The agent app now exposes one bounded probe route, `GET /api/geo/health`,
alongside the MLflow Agent Server chat proxy. The route returns HTTP 200 with
`{"status":"ok"}` and does not accept or forward user-controlled URLs or
geometry.

## Automated evidence

Run from the repository root:

```powershell
cd apps\agent-fpac-soil-openai-sdk
uv run --frozen --python 3.11 pytest tests\test_custom_routes.py -q
```

The focused test verifies:

- the custom route is registered on the exported FastAPI app;
- it is ordered after the Agent Server `/invocations` route;
- it returns the expected status and body;
- an unknown `/api/geo/*` path does not resolve to the probe response. The
  current local chat-proxy middleware may return 503 for an unknown path; this
  is explicit non-success behavior, not an implemented forwarding route.

## Probe procedure

For a local or deployed app, issue:

```powershell
curl.exe -i https://<app-host>/api/geo/health
```

Expected response: HTTP 200 and `{"status":"ok"}`. A non-200 response, proxy
rewrite, timeout, or missing route is an explicit failure; future map routes
remain blocked until the route is reachable through the actual app URL.

## Future route boundaries

This probe does not implement map behavior. A future `/api/geo/basemaps` route
must be a finite, app-owned catalog with validated entries and attribution.
A future `/api/geo/proxy/{service}` route must use a fixed service allowlist,
validated operation/parameters, bounded response sizes and timeouts, and
explicit rate limits. It must not become unrestricted URL forwarding or a
general tile proxy. File conversion and AOI geometry handling are also outside
this task.
