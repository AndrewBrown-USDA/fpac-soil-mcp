## Evidence and endpoint details

### USGS The National Map

Tested:

```text
GET https://basemap.nationalmap.gov/arcgis/rest/services/USGSTopo/MapServer?f=pjson
Origin: https://example.invalid
```

Observed HTTP 200, `Content-Type: text/plain; charset=UTF-8`, and `Access-Control-Allow-Origin: *`. The response identifies USGS Topo as a cached tile basemap service. The planned research names the related USGSTopo, USGSImageryOnly, USGSImageryTopo, and USGSShadedReliefOnly services; only USGSTopo was probed here.

The endpoint is HTTPS. ArcGIS cached tiles generally require a service-specific tile URL template; the exact `{z}/{x}/{y}` or ArcGIS tile path to use in MapLibre was not validated in a browser. Attribution must identify USGS/The National Map and any service-specific notices shown by the service metadata.

### USDA NRCS SSURGO

The repository research identifies these official services:

```text
https://SDMDataAccess.sc.egov.usda.gov/Spatial/SDM.wms
https://SDMDataAccess.sc.egov.usda.gov/Spatial/SDMWGS84Geographic.wfs
```

Tested capabilities requests:

```text
GET .../Spatial/SDM.wms?SERVICE=WMS&VERSION=1.1.1&REQUEST=GetCapabilities
GET .../Spatial/SDMWGS84Geographic.wfs?SERVICE=WFS&VERSION=1.1.0&REQUEST=GetCapabilities
Origin: https://example.invalid
```

Both returned HTTP 200 and XML capabilities. Both returned `Access-Control-Allow-Origin: *`; the WMS response also returned `Access-Control-Allow-Headers: Content-Type` and `Access-Control-Allow-Methods: GET,POST,OPTIONS`. The WMS capabilities identify the service as the NRCS Soil Data Mart Data Access Web Map Service and describe NRCS SSURGO soils.

The WMS is the likely browser overlay path, but the exact `LAYERS`, CRS/SRS, image format, bounding-box template, scale thresholds, and response size limits were not validated by a browser map request. WFS is more appropriate for bounded feature requests than an unrestricted overlay. Attribution should identify NRCS Soil Data Mart/SSURGO and the applicable survey vintage.

The repository's existing live tests prove backend SDA tabular and TIGERweb client behavior, not browser CORS or WMS/WFS rendering. The live tests are opt-in (`live_network`) and are not evidence of app-context reachability.

### Census TIGERweb

Tested:

```text
GET https://tigerweb.geo.census.gov/arcgis/rest/services/TIGERweb/Urban/MapServer/0?f=pjson
Origin: https://example.invalid
```

Observed HTTP 200. The response identifies layer 0 as “2020 Urban Areas” and the 2020 Census January 1, 2020 vintage. With the supplied `Origin`, the response returned `Access-Control-Allow-Origin: https://example.invalid`; no allow-headers or allow-methods headers were observed.

The endpoint is HTTPS and uses an ArcGIS REST layer. The exact browser query form, geometry response size, pagination, and whether all required production requests receive the same CORS behavior remain unverified. Attribution must identify the U.S. Census Bureau TIGERweb service and 2020 vintage.

## Custom URL security constraints

User-supplied basemap URLs are not approved as arbitrary forwarding. A future implementation must:

1. Require HTTPS and reject HTTP, loopback, link-local, private, ambiguous, or otherwise unsafe destinations.
2. Validate the URL template against an explicit XYZ/WMTS/WMS grammar and reject unexpected schemes, credentials, fragments, and uncontrolled query components.
3. Use a configured host/service allowlist (or catalog-only mode); do not fetch arbitrary user URLs through the backend.
4. Prevent SSRF on every redirect and DNS resolution, including rebinding and alternate IP representations.
5. Bound tile/image response size, timeouts, redirects, request rate, and content types.
6. Require and display attribution supplied by the catalog/service, without treating user text as trusted HTML.
7. Keep any future proxy service-specific and constrained; never add a generic `/proxy/{url}` or unrestricted external forwarding endpoint.
