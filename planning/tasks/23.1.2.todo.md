Define a stable SDA provenance contract for productivity ratings and interpretations without relabeling non-NCCPI indexes or changing query behavior.

## Tasks
- [ ] Trace `SDAClient.get_productivity_ratings` from index normalization through fixed/dynamic SQL selection and response-row parsing.
- [ ] Trace `SDAClient.get_interpretations`, including rule-name validation/catalog lookup and the existing interpretation response keys.
- [ ] Identify the existing SDA rule/catalog key (`rule_name`, `mrulename`, or the validated attribute metadata name) that downstream consumers can use as rating provenance.
- [ ] Preserve existing `numeric_rating`, `rating_class`, `rated_pct`, `total_pct`, sentinel handling, validation, and normalized `index_type` semantics.
- [ ] Add the smallest normalization-only change in `src\fpac_soil_mcp\sda_client.py` so each returned productivity rating carries the selected SDA rule/catalog provenance.

- [ ] Cover missing-row/unrated results with the same provenance contract where applicable, without changing existing caveats or validation errors.
- [ ] Document the exact returned provenance key in the affected function docstring or typed return contract for downstream polygon/scoring consumers.
- [ ] Keep all SQL templates, network calls, allowlist/catalog validation, and input validation unchanged unless required by the narrowly scoped normalization.
- [ ] Run the targeted validation command: `uv run pytest tests\test_sda_client.py`.

## Scope
- Only `src\fpac_soil_mcp\sda_client.py` may be changed during implementation.
- Do not edit models, polygon analysis, tools, tests, query templates, manifests, or documentation outside the function contract/docstring.

## Notes
- The execution plan requires generic provenance, not an NCCPI alias; provenance must identify the SDA interpretation rule/catalog or attribute source selected for the requested index.
- Existing response keys and validation behavior are the compatibility boundary. Prefer a derived source value from already-selected rule/attribute metadata over new SQL or network behavior.
- Acceptance is the focused SDA client test file only; full-suite and repository-wide Ruff verification belong to later tasks.
