# 40.2.1 AOI handoff decision

## Status

**Blocked — do not enable AOI integration.**

## Decision

The eventual AOI workflow must use explicit backend pre-dispatch: the UI keeps
raw geometry in session-only browser state, an explicit screening action sends
it to a dedicated backend path, and only a bounded result summary plus opaque
identifiers may enter model context or telemetry. The app remains a separate
MCP client and must call deployed MCP tools rather than adding wrapper tools.

Raw coordinates, WKT/GeoJSON, bounding boxes, and parcel properties are
prohibited from prompts, ordinary history, traces, and persistent storage.
`map_layers`/the authoritative visualization envelope is not approved here;
M3 remains out of scope.

## Blocker

The current MLflow decorator/autologging arrangement does not prove that
`custom_inputs` are redacted before trace capture. Handler-level sanitization
can protect model inputs and history but cannot satisfy the pre-trace
requirement. The platform must provide an earlier request hook or equivalent
instrumented evidence before AOI requests are enabled.

## Follow-up acceptance

Reopen only with:

1. A frontend/template probe showing the exact `custom_inputs` request shape.
2. A probe showing whether `custom_outputs.map_layers` survives the adapter.
3. Capture-order evidence proving geometry is absent before automatic tracing.
4. Offline tests covering invoke and stream paths plus history exclusion.
5. Session-only lifecycle and no durable AOI storage.
