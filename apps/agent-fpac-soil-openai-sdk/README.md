# FPAC Soil Agent App

A Databricks App that serves the FPAC Soil agent. It has a built-in chat UI and also exposes an API endpoint for invoking the agent. The app started from the Databricks `agent-openai-agents-sdk` template.

The agent input and output format are defined by MLflow's ResponsesAgent interface, which closely follows the [OpenAI Responses API](https://platform.openai.com/docs/api-reference/responses) interface. See [the MLflow docs](https://mlflow.org/docs/latest/genai/flavors/responses-agent-intro/) for input and output formats for streaming and non-streaming requests, tracing requirements, and other agent authoring details.

## FPAC Soil configuration

This app is the FPAC Soil agent. It helps USDA staff run preliminary Farmland Protection Policy Act (FPPA) screening by calling the tools on the deployed `mcp-fpac-soil` MCP server. Its system prompt is in `agent_server/prompts/system_prompt.txt`.

Answers are preliminary screening only. They are based on SSURGO soil inventory data under 7 CFR Part 657 and are not an official FPPA determination, a Land Evaluation and Site Assessment (LESA) score, or a completed Form AD-1006 or Form NRCS-CPA-106.

### Environment variables

| Name | Default | Purpose |
| --- | --- | --- |
| `AGENT_MODEL` | `models.ai.gpt-5-6-luna` | Unity Catalog model service, called through AI Gateway (`/ai-gateway/mlflow/v1`). In `app.yaml` it comes from the `llm-endpoint` resource (`valueFrom`). If unset or blank, the default is used. |
| `FPAC_MCP_APP` | unset | Name of the fpac-soil-mcp server app. In `app.yaml` it comes from the `mcp_server` app resource (`valueFrom`), and the app looks up that app's URL once per process and adds `/mcp`, so production and dev agent apps differ only in their `mcp_server` resource. If set but not resolvable, the agent runs without tools rather than using another server. |
| `FPAC_MCP_URL` | `https://mcp-fpac-soil-7474654188777746.aws.databricksapps.com/mcp` | Explicit MCP URL for local runs and tests; overrides `FPAC_MCP_APP`. Not set in the deploy files. |
| `FPAC_MCP_TIMEOUT_SECONDS` | `180` | MCP client timeout in seconds. Must be a positive number. |

GPT-5 models are called with `reasoning_effort="none"`, which they need for tool calling.

### Required grants

The agent calls the MCP server as the app's service principal, not on behalf of the user. The app needs two resources:

* An App resource `mcp_server` for `mcp-fpac-soil` with `CAN_USE`. This grants the service principal access to the MCP server. Apps-hosted MCP servers accept OAuth only, not PATs.
* A **Model** resource `llm-endpoint` for the configured Unity Catalog model service (for example `models.ai.gpt-5-6-luna`) with `EXECUTE`. The Apps UI no longer offers a Serving endpoint resource, and the legacy `databricks-*` endpoint names are no longer served (AI Gateway returns 403 "no longer available"; `/serving-endpoints` returns 404 `ENDPOINT_NOT_FOUND` for UC names).

Both are declared in `databricks.yml` (`llm-endpoint` as `uc_securable` with `securable_type: MODEL_SERVICE`) and `llm-endpoint` in `manifest.yaml` (`uc_securable_spec`). For the UI-created app, add them on the app's Apps page.

Note: `databricks-claude-sonnet-5-5` is disabled in this workspace (403 `PERMISSION_DENIED`, checked 2026-10-22). Do not use it as `AGENT_MODEL`.

### Deploying

The app was created in the UI and deploys from its git source. Set the git source branch to `main`, keep `source_code_path` as `apps/agent-fpac-soil-openai-sdk`, and redeploy. Do not run `databricks bundle deploy` for this app.

The chat frontend is vendored in `frontend/`: the whole
`databricks/app-templates/e2e-chatbot-app-next` folder from upstream base commit
`0e572976459aafa3d41047067382cb9a6c015d52`, owned by this repo, with local
changes listed in
[ADR 0015](../../docs/decisions/0015-vendored-agent-app-frontend.md). It is an
npm workspace (`client/`, `server/`, `packages/*`) with one root
`package-lock.json`, regenerated by npm when dependencies change. Upstream `.claude/`, `CLAUDE.md`, `tests/`,
`playwright.config.ts`, `app.yaml`, `databricks.yml` and `manifest.yaml` are
not vendored. To update, follow the ADR 0015 update procedure:
re-copy the folder at the new commit, re-apply the listed local changes,
regenerate the lockfile, and rerun the checks.

The frontend needs Node 22 (the Databricks Apps runtime is 22.16). From the
repository root:

```bash
make app-frontend-check   # npm ci, read-only biome lint, npm run build
make app-check            # Python lint and tests only; no npm needed
```

Do not run the upstream `npm run lint`; it rewrites files (`--write --unsafe`).
There is no typecheck target (see ADR 0015).

The UI adds a map panel next to the chat
([ADR 0016](../../docs/decisions/0016-out-of-band-aoi-screening-handoff.md)):
draw a polygon or rectangle, or paste or upload GeoJSON, then run a
preliminary screening through `POST /api/geo/screen`. The route calls the MCP
tools directly, without the model or a trace, and returns map layers for the
browser plus a summary. The AOI is attached to the current chat (one per
chat, shown as a chip above the input, with a Detach control) and kept in
browser session storage. Every chat turn sends it as
`custom_inputs.active_aoi`; the agent sees the AOI reference and summary, and
the agent server swaps the geometry into tool calls that name the reference,
so you can ask follow-up questions (for example a preliminary LESA) without
pasting GeoJSON. Geometry appears in chat traces and app logs; do not draw or
paste personal data or Section 1619 producer data outside an environment
approved for it.

Map results ([ADR 0017](../../docs/decisions/0017-server-map-result-contract.md)):

* `analyze_farmland_by_polygon`, `analyze_corridor_fppa` and
  `get_soil_polygons_by_geometry` return a `map` block. The model's calls use
  `include_map=false` (layer list, legends and sources, no geometry). `/api/geo/screen` and `/api/geo/map` ask for
  `include_map=true` and the panel draws the server's layers with the server's
  legends, simplification notes and size-limit warnings. Corridor results
  include each alternative's footprint and farmland.
* `POST /api/geo/map` backs "Show on map" on completed tool cards for those
  three tools (`geo.MAP_TOOLS`): body `{tool, arguments, active_aoi}`; only
  those tools are allowed (400 otherwise), `include_map` is forced on, and an AOI reference in the
  arguments is replaced only by the matching active AOI. Like
  `/api/geo/screen`, it is untraced and logs no request bodies.
* Context layers ("Layers" button in the map's top-right corner, all off by
  default):
  SSURGO map units (SDA WMS, from zoom 12), TIGERweb counties (from zoom 6) and
  Census 2020 urban areas (from zoom 7). The catalog is fixed in
  `overlays.ts`; the browser loads these public services directly, so map tile
  bounds and clicked points go to USDA NRCS and the Census Bureau.
* Clicking the map (no drawing tool active) shows an identify popup for a drawn
  farmland polygon under the click (map unit name, symbol, farmland class,
  acres and productivity, as the server sent them) and for each context layer
  that is on. With neither, a short hint says so and links to the Layers
  control. County and urban results offer "Use as AOI", which loads the
  exact outline and refuses it above 2000 vertices instead of simplifying.
  SSURGO identify has no farmland class; run screening for that.

### Local Site Assessment trial (headless)

`make trial-local` (repo root) is an opt-in stand-in for the dev-app trial. It starts
its own MCP server on a free port (Streamable HTTP, `/mcp`), then drives this app's
real `McpServer` client, criteria-resource validation, interview tools, and
confirmed-summary gate with a scripted model. It needs network access to USDA SDA, no
Databricks or model credentials, and is not part of `make check` or `make app-test`.
Use `uv run python scripts/trial_local.py --mcp-url http://127.0.0.1:PORT/mcp` here to
reuse a running server. See `planning/STATE_52.md` for what it cannot reproduce.

### Dev trial apps

Branch trials use two dev apps deployed from git on the feature branch, so the
production apps stay on `main`:

* `mcp-fpac-soil-dev`: the MCP server from the branch.
* `agent-fpac-soil-dev`: this app from the branch, with its `mcp_server`
  resource pointing at `mcp-fpac-soil-dev` (`CAN_USE`). `FPAC_MCP_APP` comes
  from that resource, so `app.yaml` needs no branch-specific URL.

Both have auto-deploy on; every push to the branch redeploys both. Record
trial deployments and results under `planning/evidence/`.

### MCP timeout

The client timeout is 180 seconds, not the 20-second default. Some tools, such as preliminary LESA and corridor analysis, query several USDA and Census services and can run longer than 20 seconds. 180 seconds matches the timeout used by the JS test harness.

If the MCP server cannot be reached, the agent tells the user that the tools are unavailable instead of answering from memory.

## Local development

1. **Set up your local environment**
   Install `uv` (python package manager), `nvm` (node version manager), and the Databricks CLI:

   - [`uv` installation docs](https://docs.astral.sh/uv/getting-started/installation/)
   - [`nvm` installation](https://github.com/nvm-sh/nvm?tab=readme-ov-file#installing-and-updating)
     - Run the following to use Node 22 LTS:
       ```bash
       nvm use 22
       ```
   - [`databricks CLI` installation](https://docs.databricks.com/aws/en/dev-tools/cli/install)

2. **Set up local authentication to Databricks**

   In order to access Databricks resources from your local machine while developing your agent, you need to authenticate with Databricks. Choose one of the following options:

   **Option 1: OAuth via Databricks CLI (Recommended)**

   Authenticate with Databricks using the CLI. See the [CLI OAuth documentation](https://docs.databricks.com/aws/en/dev-tools/cli/authentication#oauth-user-to-machine-u2m-authentication).

   ```bash
   databricks auth login
   ```

   Set the `DATABRICKS_CONFIG_PROFILE` environment variable in your .env file to the profile you used to authenticate:

   ```bash
   DATABRICKS_CONFIG_PROFILE="DEFAULT" # change to the profile name you chose
   ```

   **Option 2: Personal Access Token (PAT)**

   See the [PAT documentation](https://docs.databricks.com/aws/en/dev-tools/auth/pat#databricks-personal-access-tokens-for-workspace-users).

   ```bash
   # Add these to your .env file
   DATABRICKS_HOST="https://host.databricks.com"
   DATABRICKS_TOKEN="dapi_token"
   ```

   See the [Databricks SDK authentication docs](https://docs.databricks.com/aws/en/dev-tools/sdk-python#authenticate-the-databricks-sdk-for-python-with-your-databricks-account-or-workspace).

3. **Create and link an MLflow experiment to your app**

   Create an MLflow experiment to enable tracing and version tracking.

   Create the MLflow experiment via the CLI:

   ```bash
   DATABRICKS_USERNAME=$(databricks current-user me | jq -r .userName)
   databricks experiments create-experiment /Users/$DATABRICKS_USERNAME/agents-on-apps
   ```

   Make a copy of `.env.example` to `.env` and update the `MLFLOW_EXPERIMENT_ID` in your `.env` file with the experiment ID you created. The `.env` file will be automatically loaded when starting the server.

   ```bash
   cp .env.example .env
   # Edit .env and fill in your experiment ID
   ```

   See the [MLflow experiments documentation](https://docs.databricks.com/aws/en/mlflow/experiments#create-experiment-from-the-workspace).

4. **Test your agent locally**

   Start up the agent server and chat UI locally:

   ```bash
   uv run start-app
   ```

   Query your agent via the UI (http://localhost:8000) or REST API:

   **Advanced server options:**

   ```bash
   uv run start-server --port 8001 # change the port the server listens on
   uv run start-server --workers 4 # run the server with multiple workers
   ```

   - Example streaming request:
     ```bash

     -d '{ "input": [{ "role": "user", "content": "hi" }], "stream": true }'
     ```

## Modifying your agent

See the [OpenAI Agents SDK documentation](https://platform.openai.com/docs/guides/agents-sdk) for more information on how to edit your own agent.

Required files for hosting with MLflow `AgentServer`:

- `agent.py`: Contains your agent logic. Modify this file to create your custom agent. For example, you can [add agent tools](https://docs.databricks.com/aws/en/generative-ai/agent-framework/agent-tool) to give your agent additional capabilities
- `start_server.py`: Initializes and runs the MLflow `AgentServer` with agent_type="ResponsesAgent". You don't have to modify this file for most common use cases, but can add additional server routes (e.g. a `/metrics` endpoint) here

**Common customization questions:**

**Q: Can I add additional files or folders to my agent?**
Yes. Add additional files or folders as needed. Ensure the script within `pyproject.toml` runs the correct script that starts the server and sets up MLflow tracing.

**Q: How do I add dependencies to my agent?**
Run `uv add <package_name>` (e.g., `uv add "mlflow-skinny[databricks]"`). See the [python pyproject.toml guide](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/#dependencies-and-requirements).

**Q: Can I add custom tracing beyond the built-in tracing?**
Yes. This template uses MLflow's agent server, which comes with automatic tracing for agent logic decorated with `@invoke()` and `@stream()`. It also uses [MLflow autologging APIs](https://mlflow.org/docs/latest/genai/tracing/#one-line-auto-tracing-integrations) to capture traces from LLM invocations. However, you can add additional instrumentation to capture more granular trace information when your agent runs. See the [MLflow tracing documentation](https://docs.databricks.com/aws/en/mlflow3/genai/tracing/app-instrumentation/).

**Q: How can I extend this example with additional tools and capabilities?**
This template can be extended by integrating additional MCP servers, Vector Search Indexes, UC Functions, and other Databricks tools. See the ["Agent Framework Tools Documentation"](https://docs.databricks.com/aws/en/generative-ai/agent-framework/agent-tool).

## Tests

The tests run offline. Databricks clients and the MCP server are mocked.

```bash
uv run pytest tests -q
```

Agent evaluation lives in the repository's `eval/databricks/` (T1), not in this app.

The app's native system prompt follows the versioned FPPA screening policy
asserted across the app, FastMCP prompts, Databricks prompts, and Pi's
constructed prompt path. It preserves FPPA-only scope, refuses unrelated
requests, avoids official/legal determinations and siting recommendations,
does not overinterpret farmland classes or urban screening, and keeps
unknown/partial/unavailable information explicit without inventing values.
Shared adversarial cases
and deterministic policy assertions are documented in the
[repository evaluation overview](../../README.md#prompt-policy-and-adversarial-cases).

Orchestration 46's benchmark artifact is a manifest-only dry run, not
deployed-app or service performance evidence; model-assisted results were
not run. See the [46.4.2 evidence](../../planning/evidence/46.4.2-performance.md)
and [state report](../../planning/STATE_46.md).

## Querying the deployed app

Deploy through the app's git source as described in [Deploying](#deploying). The deployed app uses `app.yaml`; `databricks.yml` documents the same env vars and resources.

   You must use a Databricks OAuth token to query agents hosted on Databricks Apps. See [Query an agent](https://docs.databricks.com/aws/en/generative-ai/agent-framework/query-agent) for full details.

   **Using the Databricks OpenAI client (Python):**

   ```bash
   uv pip install databricks-openai
   ```

   ```python
   from databricks.sdk import WorkspaceClient
   from databricks_openai import DatabricksOpenAI

   w = WorkspaceClient()
   client = DatabricksOpenAI(workspace_client=w)

   # Non-streaming
   response = client.responses.create(
       model="apps/<app-name>",
       input=[{"role": "user", "content": "hi"}],
   )
   print(response)

   # Streaming
   streaming_response = client.responses.create(
       model="apps/<app-name>",
       input=[{"role": "user", "content": "hi"}],
       stream=True,
   )
   for chunk in streaming_response:
       print(chunk)
   ```

   **Using curl:**

   ```bash
   # Generate an OAuth token
   databricks auth login --host <https://host.databricks.com>
   databricks auth token
   ```

   ```bash
   # Streaming request
   curl --request POST \
     --url <app-url>.databricksapps.com/responses \
     --header "Authorization: Bearer <oauth-token>" \
     --header "Content-Type: application/json" \
     --data '{
       "input": [{ "role": "user", "content": "hi" }],
       "stream": true
     }'
   ```

   ```bash
   # Non-streaming request
   curl --request POST \
     --url <app-url>.databricksapps.com/responses \
     --header "Authorization: Bearer <oauth-token>" \
     --header "Content-Type: application/json" \
     --data '{
       "input": [{ "role": "user", "content": "hi" }]
     }'
   ```

### FAQ

- For a streaming response, I see a 200 OK in the logs, but an error in the actual stream. What's going on?
  - This is expected behavior. The initial 200 OK confirms stream setup; streaming errors don't affect this status.
- When querying my agent, I get a 302 error. What's going on?
  - Use an OAuth token. PATs are not supported for querying agents.
